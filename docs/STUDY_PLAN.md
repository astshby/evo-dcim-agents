# 论文框架研究路线

## 总目标

理解每篇论文改变了什么、依赖什么反馈、维护什么状态、如何实现以及实验支持到哪一层，再考虑用于 DCIM。
OpenC² 的生成与硬件验证为后续提供应用场景和评价器，不替代框架机制研究。

## 每篇的统一验收

1. 机制图：输入、决策、环境、反馈、存储、更新点。
2. 一轮可手算或离线追踪的例子：明确每个状态字段和数值含义。
3. 论文图/算法/公式到源码函数的对应表，记录公开实现差异。
4. 原始独立基线、最小复跑命令、模型/数据/环境依赖及成本。
5. 固定其他条件的对照或消融，确认收益来自哪个机制。
6. 对 DCIM 可迁移的部分、需要新做的适配、不能直接外推的结论。

未完成项保留待检查状态。

## 阶段

A：源码与本地环境准备。
B：逐篇独立研究与最小验证，每轮一个小目标。
C：相同任务和预算下比较，再取舍机制。
D：验证组合候选，统一状态、事件、记忆版本和评价条件。
E：把 OpenC² 受控任务接成应用场景；硬件功能、物理规则与 PPA 分别验收。

此前 EvoTest + ACE + JitRL 蓝图只属于 D 的候选。
